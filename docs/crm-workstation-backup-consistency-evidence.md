## Наблюдения

- `docker inspect` показал RW bind `/opt/autostopcrm/data` в `autostopcrm`; контейнер работает, healthy, restart policy `always`. У `autostop-searxng` отдельный RW bind в `data/searxng/cache` и RO bind в `data/searxng/config`. Store не имеет прямого mount корня CRM. `searxng` — отдельная служба Compose; см. `/opt/autostopcrm/docs/agent/module_operations/crm_runtime.md` и `docker-compose.yml`.
- В CRM data находятся `state.json`, `change_feed.sqlite3` и его WAL/SHM, вложения, документы, общие файлы и индекс, аудит, печатные формы, настройки, пользователи и OAuth state. Данные CRM, исключения вроде логов, служебных кэшей и старых backup, а также нужность прочих каталогов надо определить по версии и проверить при восстановлении; простое включение всей папки не означает CRM-only. Данные могут содержать секреты, поэтому состав и место копии должны быть защищены.
- OAuth state зашифрован отдельным стабильным `AUTOSTOP_MCP_OAUTH_STATE_KEY`, находящимся вне файла состояния: `/opt/autostopcrm/src/minimal_kanban/mcp/oauth_provider.py:165` и `/opt/autostopcrm/docs/OPERATIONS_RUNBOOK.md:644`. Наличие файла без доступного при восстановлении соответствующего ключа не подтверждает восстанавливаемость. Ключ не записывать в репозиторий или отчёт.
- `lsof +D /opt/autostopcrm/data` во время проверки показал процесс Python внутри контейнера CRM. Это наблюдение в конкретный момент, а не доказательство отсутствия будущих процессов на хосте. Автономные клиентские API/MCP вызовы создают другие пути записи через CRM. Manager MCP, scheduler и work-Telegram wake на момент чтения работали; scheduler использует операции CRM change feed, включая регистрацию и ACK (`autostop_manager/automation_jobs.py:96`, CRM runtime card, строка Change feed). Неизвестные результаты внешних операций нельзя автоматически переигрывать.
- JsonStore использует `state.lock` (`/opt/autostopcrm/src/minimal_kanban/storage/json_store.py:255`), но другие хранилища используют собственные lock: `shared_files_index.lock`, `agent.lock`, `mcp-oauth-state.lock`, printing и operator activity. Вложение сначала записывается на диск, затем добавляются метаданные (`services/card_attachments.py:168`); общий файл и индекс обрабатываются под другим lock (`services/shared_files_service.py:215`). Один `state.lock` не останавливает всё дерево.
- Маркер maintenance не является доказанной общей блокировкой: `/opt/autostopcrm/src/minimal_kanban/api/server.py:1882` блокирует определённые маршруты и отдельно допускает технические операции. Manager `scripts/autostop-complete-backup.py:614` архивирует файлы, сверяет их вокруг SQLite snapshot под `state.lock`, а `agent` снимает отдельно. Это механизм компонентной согласованности, он также включает Store и не является доказанным единым CRM-only снимком.
- `/opt/autostopcrm/docs/OPERATIONS_RUNBOOK.md:151` указывает на возможные зафиксированные данные в WAL и использование SQLite backup API; нельзя копировать только основной файл живой базы. Общий offline runbook (`:810–840`) требует остановки intake, потребителей, Manager, CRM, Store и watchdog для совместного изменения компонентов. Из него не следует, что ради CRM-only надо автоматически останавливать Store.
- При чтении `autostop-app-watchdog.timer` был inactive/disabled, его service inactive; `autostopcrm-watchdog.timer` и service отсутствовали. Состояние процессов и таймеров меняется: перед каждым окном нужно читать фактическое состояние, включая уже запущенное восстановление. `/opt/autostopcrm/scripts/production_watchdog.py` предусматривает deploy lock; у disk-maintenance также есть CRM deploy lock. Совпадение имени lock само по себе не доказывает, что все сторонние writers ему следуют.

## Что ещё доказать до включения

1. Определить полный набор нужных для восстановления путей и все процессы, способные их менять, включая host maintenance/deploy, отложенные операции, обращения через API и побочные записи при чтении. Повторить фактическую проверку всех mounts, процессов, таймеров и активных операций в целевой конфигурации; наличие только текущего `lsof` недостаточно. Явно исключить `searxng/cache` и подтвердить, что ни один необходимый для CRM путь не находится за пределами выбранной границы.
2. Построить единый протокол quiescence: закрыть новый приём и дождаться завершения выполняющихся операций, исключить конкурирующие deploy/maintenance и обнаруженные прямые записи, остановить требуемых writers и проверить их фактическую остановку. Установить поведение входящих очередей и состояние незавершённых эффектов; не возобновлять или переигрывать их вслепую. Store останавливать только при отдельном подтверждённом требовании.
3. Сохранить исходное состояние контролируемых служб до остановки; записывать намерение и этапы с защитой от внезапного прекращения процесса. Продумать восстановление после сбоя процесса, Docker и перезагрузки с учётом `restart=always`: возвращать только ранее работавшие службы, не включать выключенное дежурство, проверять состояние и здоровье до повторной передачи. При непроверенной границе или невозможности безопасного восстановления пропустить копию и сохранить прежние.
4. Для SQLite закрыть все соединения и корректно учесть WAL либо сделать SQLite backup API в доказанной общей паузе остальных писателей. Проверить полноту файлов и совместимость снимка с зафиксированной версией CRM в одном изолированном восстановлении; копировать данные без кода. Подтвердить и безопасно сохранить доступный при восстановлении ключ OAuth, отдельно от Git.
5. Проверить предложенный протокол один раз на искусственных данных, в том числе отказ и прерывание, затем выполнить один изолированный restore согласно действующему runbook. Отдельно подтвердить безопасность адресата, защиты и публикации на ПК. Ночной таймер включать лишь после выполнения этих условий и фактического readback; эта заметка сама по себе ничего не включает.

## Минимальная доработка контролируемой остановки

Текущий SIGTERM недостаточен для доказательства завершения операций. `scripts/container_entrypoint.py` передаёт управление `main_mcp.py`; `mcp/main.py:250` обрабатывает SIGTERM и в `:78` вызывает очистку MCP, embedded agent, API и store. MCP ждёт свой поток до 10 секунд (`mcp/runtime.py:110`), agent — каждый поток до двух секунд (`agent/control.py:82`). Но `api/server.py:2456` задаёт `daemon_threads=True`, `block_on_close=False`; `ApiServer.stop()` в `:2200` ждёт поток сервера, а не работающие обработчики. Переход контейнера в stopped или `exit 0` поэтому не доказывает безопасного завершения всех запросов. Принудительное завершение при Docker timeout тем более не устанавливает результат эффекта.

Минимальная конструкция для проверки в отдельной ветке CRM:

1. Добавить в CRM явную локальную защищённую команду и общий контроллер admission/drain: атомарно закрывать новые внешние MCP-вызовы и создание фоновых задач, ждать фактического окончания уже допущенных MCP tools и agent worker, после этого закрывать все внешние API-операции и ждать каждого активного HTTP handler. Учесть OAuth, change feed, фоновые задачи, зависимые внутренние API-вызовы и операции чтения с побочной записью: например, `agent_status` запускает `trigger_scheduled_tasks` (`agent/control.py:145`). Доступ разрешённых зависимых вызовов нужно сохранить до завершения их родительской операции, не открывая обход для новых внешних вызовов.
2. В `mcp/tool_execution.py` учитывать завершение фактических фоновых функций, а не только отменённого запроса; текущее удержание слота после отмены — полезная основа, но наружной общей гарантии drain нет. В `api/server.py` считать полную жизнь каждого handler и предоставлять ограниченное ожидание нуля. В `agent/control.py` запретить новые задачи и дождаться выполняемых, не переходя к копированию при timeout. Доказать, что все прочие собственные источники записи охвачены. Экспортировать только технические статусы, без содержимого и секретов.
3. В Manager реализовать отдельный backup-контракт координации с устойчивым идентификатором попытки, блокировкой конкурирующих обслуживания/запусков, атомарной записью исходных состояний и независимой аварийной процедурой возврата после сбоя и перезагрузки. Перепроверять идентичность контейнера, ограничения внешних host writers и watchdog перед копированием и до публикации. Переиспользовать имеющиеся гарантии только после проверки границ: scheduler при обычном shutdown дожидается CRM HTTP workers (`automation_daemon.py:410–443`), а `set_global_hold` разрешён system actor только в release procedure (`docs/agent/references/telegram-runtime.md:153`); это не готовый backup drain.
4. Дополнить прицельными синтетическими тестами: handler с задержанной записью, отменённый MCP запрос с ещё выполняющимся worker, вложенный API-вызов ранее допущенной операции, активный agent worker, отказ/timeout на каждом этапе, конкурирующий deploy и попытка нового запроса во время барьера. Доказать, что результат не публикуется без drain, после отказа приём восстановлен, исходно выключенное не включается, внешние эффекты не переигрываются. Отдельно проверить внезапное завершение координатора и reboot с Docker `restart=always`; изолированный restore выполнить один раз при приёмке.

Это направление, а не готовый контракт: отдельно требуется проверить авторизацию локальной команды, все обходные пути и упорядочение восстановления после перезагрузки до любого включения таймера.

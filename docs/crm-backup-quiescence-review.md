# Проверка подготовленных примитивов остановки CRM

Проверены CRM-коммиты `9c57d86f8f08f9de8fe3a62c49bbe6ace1f1e6c1` и
`0082e77c89fd2c5a66a1e885240e6191d0307808` в worktree
`/root/.codex/worktrees/crm-backup-quiescence-20261031`. Это подготовленный
код, не установленная функция и не доказательство согласованной копии CRM.

- HTTP admission учитывает соединение до чтения первой строки запроса. Клиент,
  который подключился и ничего не отправляет, удерживает счётчик; тайм-аут
  чтения первой строки в этом обработчике не установлен. Изолированная проверка
  с методом из исходника подтвердила: при открытом пустом соединении drain не
  завершается, после закрытия соединения завершается. При тайм-ауте ожидания
  остановку нельзя считать успешной: это может приводить к пропуску копии.
- `ApiServer.stop()` сам не ожидает drain; потоки HTTP-обработчиков daemon и
  не ожидаются при закрытии. Следовательно, возврат `stop()` сам по себе не
  подтверждает завершение уже начатых операций.
- `register_agent_gateway_v2` создаёт `ToolExecutor` локально и не передаёт
  ссылку владельцу runtime. Внешний контроллер пока не может штатно закрыть
  и проверить именно этот executor.
- Счётчик executor охватывает отдельные синхронные вызовы, но не весь native
  async workflow между вызовами. При нулевом счётчике такой workflow ещё может
  быть активен и после возобновления перейти к следующей стадии. Для границы
  согласованности нужны отдельный учёт полного жизненного цикла MCP-запроса
  и проверка прочих writers; счётчика одного executor недостаточно.

В просмотренных ветках отмены executor сохраняет учёт уже работающей функции
до её фактического возврата; отменённый до старта ticket не запускает функцию.
Явной гонки двойного освобождения в этих ветках не обнаружено. Эта проверка
не заменяет интеграционные проверки будущего shutdown и всех writers.

# Остановка writers CRM и возврат служб: подготовка

Статус: разработка, согласованный snapshot не доказан и расписание не включено.
Установленный Manager при исследовании: `490edc332a3a0eeed626b1860771402170150108`;
CRM: `fe3c3c73d2800b6381ed2e1a489ec4be742d9e9c`. Текущее состояние процессов,
таймеров, mount и исходных состояний проверять заново перед реальным окном.

## Границы

- Счётчики MCP и API и пауза встроенного агента относятся только к своим
  конкретным экземплярам. Новый вход надо закрыть до ожидания уже принятых
  последовательностей, сохранив им внутренние вызовы. Затем следует учитывать
  их реальные worker threads, API и агента; OAuth, detached Manager workers и
  удалённые операции остаются отдельными источниками неопределённости.
- Встроенный scheduler после паузы сохраняет штатный catch-up просроченных
  задач. Проверка очереди и неизвестных эффектов не реализована; пауза агента
  намеренно не подтверждает готовность snapshot. Возврат нельзя превращать в
  повтор неизвестного внешнего эффекта.
- Прямые host writers, включая restore и административные скрипты, не все
  участвуют в единой блокировке. Существующий deploy lock и readback процессов
  сами по себе не закрывают все пути записи. Нужен доказанный контракт каждого
  writer и проверка конкурирующих maintenance/deploy до snapshot.
- Store не имеет прямого mount корня данных CRM. Обращения сторонних клиентов
  могут поступать в CRM по API: нужна защищённая граница входа CRM. Основания
  автоматически останавливать Store этим исследованием не установлены.

## Аварийное состояние

`scripts/crm_backup_recovery_journal.py` — изолированный журнал намерений, а
не сервисный контроллер. Он сохраняет исходные состояния и технические identity,
фиксацию намерения перед остановкой и возвратом, отказывает при неоднозначной
устойчивости и не допускает автоматический переход после смены boot. При смене
boot нужно отдельно проверить все службы, в том числе исходно выключенные:
автозапуск Docker мог изменить их состояние. Сверка identity/ownership и
фактическое изменение служб остаются обязанностью будущего контроллера.

Если закрытие журнала прервано во время активной операции, блокировка может
сохраняться до завершения процесса; автоматическое восстановление доступности
и завершение старой попытки после reboot пока отсутствуют. Не удалять журнал,
не считать receipt команд доказательством состояния и не включать ранее
выключенное. После возврата нужны независимые readback и проверка здоровья.

Кандидаты не установлены. До реального копирования необходимы общий координатор,
доказательство всех writers и очередей, управление неизвестными результатами,
а также проверки аварийного восстановления на искусственных данных. Одна
изолированная проверка восстановления CRM выполняется при приёмке по плану.

## Дополнительные результаты подготовки

В CRM source-ветке подготовлен процессный координатор отдельных API, MCP,
executor и agent fences. Он не подключён к действующему runtime; его
`backup_ready` всегда false, а полное восстановление без общей authority не
подтверждается. Проверки границ после остановки отдельных блокировок не образуют
атомарный общий снимок. Незакоммиченный следующий вариант authority находится
в том же CRM worktree и содержит воспроизведённые ошибки владения при возврате;
не применять его и не считать успешный локальный тест доказательством.

Исходный CRM watchdog проверяет deploy lock до цикла, но не держит его через
восстановление; уже начатое действие может пересечь попытку копирования. Lock
advisory и не ограждает другие Docker-клиенты. Неизвестный исход Docker CLI
требует durable marker и независимого readback, но действующие maintenance и
будущий backup этот marker пока не проверяют. Даже команда по точному ID может
включить контейнер, остановленный конкурентом между проверкой и действием.
Незакоммиченный watchdog WIP намеренно запрещает автоматическое восстановление
контейнера и сохраняет marker для проверки; это меняет обычное поведение и не
является готовым релизом. Действующий CRM watchdog unit при проверке отсутствовал.

До перехода к рабочему контроллеру нужны общая authority и привязка всех
объектов CRM, защищённая от обхода; lifecycle API/MCP; окончание неизвестных
или удалённых операций; контроль marker и прямых host writers; адресный ранний
boot fence, который не блокирует общий Docker/Store, и проверенный service
adapter с восстановлением ранее активных состояний. Не включать расписание до
доказательства этих границ и приёмки.

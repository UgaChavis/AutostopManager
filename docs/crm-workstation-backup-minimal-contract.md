## Что уже есть

Разовый переход со старой CRM отдельно разобран в
[проверке границы остановки](crm-first-transition-20261031.md).
Проверка точного старого образа нашла работающий idle gate на уровне TCP listener;
это исторический механизм для `fe3`, не процедура повторного выпуска текущей CRM.

- Docker и systemd позволяют адресно останавливать и проверять конкретные службы. Учитывать не только watchdog timer, но и уже запущенный watchdog service. Store и его backup не менять.
- `/opt/autostopcrm/scripts/agent_release_backup.py` использует штатный SQLite backup API, учитывающий WAL, и временный каталог с публикацией. Весь helper не подходит как готовый CRM-only backup: он требует базу Manager и не включает полный состав файлов CRM. Старый complete-bundle не включать.
- Действующий runbook описывает окно выпуска с остановкой intake и участников. Ежедневная CRM-only попытка использует проверенный native drain текущей CRM, stop scheduler и host writer fence; Store и его backup не меняются.
- На отдельной искусственной задаче после `SIGKILL` основного процесса systemd остановил дочерний процесс и выполнил `ExecStopPost`. Это проверка механизма на текущем сервере, а не проверка возврата CRM или перезагрузки.
- Установленный пакет передал реальный архив на ПК с независимой проверкой размера, hash и закрытого ACL. Native SFTP устранил зависание больших файлов; повтор и ротация проверены отдельно. Туннель может отсутствовать, поэтому доставка повторяется после возврата CRM.
- Первая согласованная копия реальных данных и изолированное восстановление CRM с OAuth-ключом прошли. Первая успешная запись — начальная контрольная точка, не работа ежедневного таймера; первый календарный запуск назначен на 02.11.2026 02:00 Красноярск. Реальную перезагрузку хоста не выполняли; boot и crash-сценарии проверены изолированно.
- У MCP есть отдельный пул потоков AnyIO: искусственная проверка показала, что отменённая задача может продолжать работу после `shutdown_default_executor()`. Нельзя считать этот вызов доказательством завершения всех writers. Ошибка закрытия встроенного агента при незавершённых потоках тоже должна запрещать снимок.
- Работающий Manager scheduler посылает `register`/`ack` в CRM; API drain должен дождаться принятых обработчиков. Некоторые инструменты MCP используют отдельные пулы Manager, которые не дренируются при остановке MCP и способны менять Store или состояние Manager; прямые записи этих пулов в CRM не доказаны. Store останавливать только из-за этого нельзя.
- На изолированном контейнере проверено: при ошибке очистки `docker stop` возвращает успех, а код выхода самого контейнера равен 1. Поэтому при остановке нужно отдельно читать код выхода именно нужного контейнера и исключать принудительное завершение; нулевой код сам по себе ещё не доказывает отсутствия внешних writers.
- Сотрудничающая дисковая очистка использует CRM deploy lock, но уже работающую операцию надо отдельно дождаться. Неустановленный сейчас CRM watchdog в исходниках освобождает lock до возможного рестарта; ручной запуск Docker и `restart=always` этим lock не ограждены.

## Необходимые условия

1. Подтверждены Windows, точный hostname, закреплённый SSH-ключ, NTFS и папка. Проверена передача и обратное чтение двух искусственных файлов с кириллицей и пробелом в пути; файлы удалены. Папка наследует право чтения другой локальной учётной записи, поэтому настоящие копии создавать сразу с закрытым ACL: это проверено на отдельном пробном файле. Свободное место и идентичность проверять заново; не подменять устройство и не сканировать сеть.
2. Утвердить состав CRM без кода, Store, старых backup и кэшей. Установить всех writers: контейнер, принятые API/MCP-запросы, агента, OAuth, host maintenance/deploy и дочерние операции. `state.lock`, одна остановка контейнера и отдельный SQLite snapshot не доказывают общий срез файлов. Подтвердить защищённое восстановление соответствующего ключа OAuth без вывода ключа.
3. Доказать, что intake закрыт, принятые записи завершены и никто не запустит writers во время копирования. CRM имел `restart=always`; обычный `docker stop`, deploy lock и остановка одного timer не решают перезапуск Docker или хоста. Нужны точные identity, исходные состояния и проверенная процедура возврата при неизвестном результате и reboot. Если состояние или владение неясно, не копировать и не повторять команду вслепую.

## Порядок одной попытки

1. Отдельный systemd timer запускает задание ежедневно в **02:00 Asia/Krasnoyarsk**, независимо от работы агента в роли M2. Проверить место, исключить одновременные попытки, устойчиво сохранить исходные состояния и намерения. При недоказанном предусловии или timeout пропустить попытку.
2. Закрыть необходимый intake, завершить начатые операции и остановить только необходимые writers; независимо проверить результат. В приватной временной папке собрать утверждённые файлы CRM с одной остановленной границы, SQLite — штатным backup API с учётом WAL. Не следовать неподтверждённым ссылкам; указать версию CRM и технический manifest без секретов и бизнес-данных.
3. При ошибке не публиковать копию и не удалять прежние. При успехе закрыть и синхронизировать файлы, затем атомарно опубликовать локальную копию. В `finally` вернуть только подтверждённо остановленные этой попыткой и исходно активные службы; проверить их состояние и здоровье CRM. Для SIGKILL и reboot обычного `finally` недостаточно: нужна отдельная проверенная сверка по сохранённым состояниям. Не переигрывать неизвестные эффекты.
4. Передавать готовую копию на подтверждённый ПК **после возврата CRM**: временное имя, проверка полученных байтов, завершение записи и атомарная публикация. Только после успеха удалить собственные завершённые копии сверх двух. Недоступный ПК не задерживает CRM; повторять передачу позже. На сервере хранить одну последнюю готовую непереданную копию; заменять предыдущую только после устойчивой публикации новой. При нехватке места пропускать новую попытку и сохранять прежнюю копию.

При вводе — одна проверка на искусственных данных и один изолированный restore по действующему runbook, включая права, версию, SQLite/WAL и ключ, без внешних эффектов; отдельно проверить отказ и недоступный ПК. Ежедневные проверки восстановления не нужны. В M2 показывать назначение, расписание, подтверждённый путь и фактические результаты копирования, возврата CRM и передачи; план не выдавать за выполненную работу.

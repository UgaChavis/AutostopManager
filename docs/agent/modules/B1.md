# B1 — Telegram-мост

B1 связывает Codex с [рабочим B2](B2.md) и [личным B3](B3.md) Telegram-аккаунтами. Выбирай нужный аккаунт и команды по задаче; точные параметры проверяй через `--help` текущего bridge CLI.

## ПОИСК И ЧТЕНИЕ

- `dialogs`, `search`, `resolve-phone` — найти диалог или адресата.
- Клиентское задание: `read --peer ... --limit 100 --job-id ... --lease ... --revision ...`. При каждом обращении прочитай всю доступную историю с исходящими: продолжай тем же peer, `--before-message-id <next_before_message_id>` и `--history-receipt <history_receipt>` предыдущей страницы до `has_more=false`. Каждая страница содержит до 100 сообщений в хронологическом порядке; курсор исключительный. Подтверди полученный в последней странице `history_receipt` через `job-history-confirm --job-id ... --lease ... --expected-revision ... --history-receipt ...`. После рестарта или смены ревизии начни чтение заново; неполное чтение не разрешает новую отправку. Административный `read --peer ...` без задания не подтверждает историю клиентского задания.
- `download --peer ... --message-id ... --job-id ... --lease ... --revision ...`, `discard-download` — получить временный файл медиа по текущему target через dry-run/apply и удалить после обработки с проверкой удаления, в том числе после ошибки.
- `monitor-target`, `monitor-read`, `monitor-context` — получить адресата и контекст текущего рабочего события.
- В durable work-входе `monitor-events` показывает также `bot_pending` и `identity_pending`. Уведомление бота отдельно от клиентской очереди; прочитай точный `monitor-read`, после обработки закрой `monitor-mark --disposition no_reply_needed`. Для `identity_pending` root может повторно установить тип через `monitor-reclassify --event-id ...`. Хранится локатор, не снимок текста: удалённое или изменённое сообщение Telegram может оказаться недоступным.

`monitor-context` не заменяет `read` с исходящими. Голос рабочего события обрабатывай [monitor-voice wrapper](../../../scripts/run-work-telegram-monitor-voice.sh) с `--event-id ... --language ru` до отправки reply: подготовка голоса требует открытого события. Фото скачай через `download`, просмотри точный временный файл через `view_image`, затем удали через `discard-download` и проверь удаление. Для скачанного аудио и видео используй [media wrapper](../../../scripts/run-work-telegram-media.sh) с `--delete-after`; он не обрабатывает фото. Проверяй очистку и после ошибки; credentials/session напрямую не читай.

## ОТПРАВКА

- `send`, `send-photo`, `send-document` — отправить текст, фото или документ.
- `send-voice` — настоящий OGG/Opus voice note только из личного B3; точный числовой private peer и приватный outbox, dry-run/apply, сверка voice/duration/MIME и скачанных байтов.
- `job-handoff` — передать текущее клиентское задание закреплённому владельцу с квитанцией этого задания.
- `owner-target`, `notify-owner` — определить закреплённого владельца и отправить самостоятельное уведомление; передачу клиентского задания выполняй через `job-handoff`.

Пишет координатор; субагенты возвращают факты и источники. Отправляй только по разрешённой задаче точному текущему адресату и reply-to. Клиентскую отправку рабочего Telegram свяжи с его job/lease, актуальной revision и kind: ack, result или clarification; параметры — по текущему `--help`. Для job-bound отправок и `job-handoff` передавай `--history-pages N` из подтверждённого чтения: мост сверяет число страниц и рассчитывает время проверки длинной истории. Используй dry-run, затем apply со свежим contract token и устойчивым idempotency key для конкретного эффекта; затем независимо перечитай результат. При неизвестном исходе сначала проверь исходящие, без слепого повтора или смены ключа.

Для разных job-bound отправок одного `kind` в одной ревизии контекста указывай разные `--effect-slot`: целое от 0 до 31, по умолчанию 0. Например, текст и отдельное фото с `kind=result` могут использовать слоты 0 и 1. Для dry-run и apply одного эффекта сохраняй тот же слот и исходный ключ; неизвестный исход сначала сверяй, не меняя слот или ключ и не начиная новую отправку. Слоты разных `kind` независимы.

Для передачи клиентского задания используй `job-handoff` с теми же job/lease, актуальной `--expected-revision` и `--reply-to-message-id` исходного клиентского события: dry-run → apply с возвращёнными token/key → независимый `job-effect-readback --effect-key` исходного эффекта. Он отправляет одно уведомление владельцу и создаёт привязанную квитанцию `handoff`; дополнительный `notify-owner` не нужен. Сообщение о передаче самому клиенту, если требуется, отправляй через `send` с `kind=result`, без внутренней CRM-ссылки. После проверки эффектов перечитай задание и заверши `job-result --outcome handoff` с актуальной revision, всеми event_ids и проверенными квитанциями этого задания, включая handoff. Обычный `send --kind handoff` для этого не используется; квитанция самостоятельного `notify-owner` не заменяет job-bound handoff.

Для `notify-owner` разреши актуальный `owner-target`, используй dry-run/apply, свежий token и один notification key на конкретное сообщение; проверь доставку. Эта привязка не меняет клиентскую роль входящих рабочего аккаунта по [B2](B2.md). При ошибке привязки или неизвестном исходе не заменяй адресат, ключ или способ отправки. Поводы клиентских уведомлений определяет клиентский скилл; самостоятельные вопросы директора — [M1](M1.md).

## СОСТОЯНИЕ

`probe`, `status`, `owner-status` показывают соединение и настройки. `monitor-status`, `monitor-events` показывают техническое состояние событий без чтения переписки.

CLI, аккаунты и служебные команды: [операционная инструкция Telegram](../references/telegram-runtime.md). Работа с диалогами и медиа: [Telegram skill](../../../.agents/skills/manage-owner-telegram/SKILL.md).

# B1 — Telegram-мост

B1 связывает Codex с [рабочим B2](B2.md) и [личным B3](B3.md) Telegram-аккаунтами. Для рабочего задания используй команду запуска Bridge из закреплённых инструкций Wake. Точные параметры проверяй через `--help` выбранного CLI.

## ПОИСК И ЧТЕНИЕ

- `dialogs`, `search`, `resolve-phone` — найти диалог или адресата.
- Клиентское задание: `read --peer ... --limit 100 --job-id ... --lease ... --revision ...`. При каждом обращении прочитай всю доступную историю с исходящими: продолжай тем же peer, `--before-message-id <next_before_message_id>` и `--history-receipt <history_receipt>` предыдущей страницы до `has_more=false`. Каждая страница содержит до 100 сообщений в хронологическом порядке; курсор исключительный. Подтверди полученный в последней странице `history_receipt` через `job-history-confirm --job-id ... --lease ... --expected-revision ... --history-receipt ...`. После рестарта или смены ревизии начни чтение заново; неполное чтение не разрешает новую отправку. Административный `read --peer ...` без задания не подтверждает историю клиентского задания.
- `download --peer ... --message-id ... --job-id ... --lease ... --revision ...`, `discard-download` — получить временный файл медиа по текущему target через dry-run/apply и удалить после обработки с проверкой удаления, в том числе после ошибки.
- `monitor-target`, `monitor-read`, `monitor-context` — получить адресата и контекст текущего рабочего события.
- В durable work-входе `monitor-events` показывает также `bot_pending` и `identity_pending`. Уведомление бота отдельно от клиентской очереди; прочитай точный `monitor-read`, после обработки закрой `monitor-mark --disposition no_reply_needed`. Для `identity_pending` root может повторно установить тип через `monitor-reclassify --event-id ...`. Хранится локатор, не снимок текста: удалённое или изменённое сообщение Telegram может оказаться недоступным.

`monitor-context` не заменяет `read` с исходящими. Голос рабочего события обрабатывай [monitor-voice wrapper](../../../scripts/run-work-telegram-monitor-voice.sh) с `--event-id ... --language ru` до отправки reply: подготовка голоса требует открытого события. Фото скачай через `download`, просмотри точный временный файл через `view_image`, затем удали через `discard-download` и проверь удаление. Для скачанного аудио и видео используй [media wrapper](../../../scripts/run-work-telegram-media.sh) с `--delete-after`; он не обрабатывает фото. Проверяй очистку и после ошибки; credentials/session напрямую не читай.

## ОТПРАВКА

- `send`, `send-photo`, `send-document` — отправить текст, фото или документ.
- `send-voice` — настоящий OGG/Opus voice note только из личного B3; точный числовой private peer и приватный outbox, dry-run/apply, сверка voice/duration/MIME и скачанных байтов.
- `job-handoff` — передать текущее клиентское задание закреплённому владельцу с квитанцией этого задания.
- `owner-target`, `notify-owner` — определить закреплённого владельца и отправить самостоятельное уведомление; передачу клиентского задания выполняй через `job-handoff`.

Пишет координатор. Субагенты возвращают факты и источники. Для каждой отправки используй точного адресата, dry-run, затем apply со свежим contract token и устойчивым idempotency key конкретного сообщения. При неизвестном исходе сначала проверь исходящую отправку по исходному ключу.

### По прямому поручению владельца

Прямое поручение владельца в доверенном чате Codex разрешает отправить текст с рабочего аккаунта одному точному личному адресату. Входящий диалог, клиентское задание, карточка CRM и повторное согласование не требуются. Мост требует root на локальном соединении. Разграничение в общей среде Codex описано в [B4](B4.md).

1. Установи точного адресата. При необходимости используй `search` или `dialogs`. Если остаётся несколько подходящих людей, уточни, кому писать.
2. Назначь сообщению устойчивый ключ. Выполни `send --work-direct --phone PHONE --text TEXT --mode dry_run --idempotency-key KEY` на рабочем мосте. Передавай номер с `+` и кодом страны либо российский номер из 11 цифр с начальной `7` или `8`. Российский мобильный номер из 10 цифр с начальной `9` мост преобразует в `+7`. Остальные номера без `+` мост отклоняет. Для `--peer PEER` укажи точный `@username`, ID подтверждённого диалога или точное имя, которое однозначно совпало с сохранённым контактом рабочего аккаунта. Если Telegram не нашёл аккаунт по номеру, сообщи об этом и запроси точный `@username`, если он есть.
3. Выполни `send --work-direct` с тем же `--phone` или `--peer`, тем же текстом и `--idempotency-key KEY`. Укажи `--mode apply` и `--contract-token TOKEN` из dry-run.
4. Сверь исход через `send-readback --idempotency-key KEY`. Если dry-run истёк, мост перезапустился или результат apply потерян, начни с этой проверки исходного ключа.

- `verified` подтверждает исходящее сообщение с указанным `message_id`. Поле `operator_reviewed` показывает, что ID установили ручной сверкой.
- `accepted_unverified` возвращает `accepted=true`, `verified=false` и `message_id` из квитанции Telegram. Сообщи владельцу, что Telegram принял отправку, а исходное сообщение удалено, изменено или недоступно для сверки. Повторная отправка запрещена. При необходимости повтори `send-readback` с тем же ключом. Успешная сверка даст `verified`.
- `not_found` означает, что в журнале нет попытки по этому ключу. Когда прежний вызов завершился, можно заново подготовить отправку с исходными параметрами и ключом.
- `unknown` означает, что исход попытки требует сверки. Сохрани ключ. После завершения попытки используй `send-readback --idempotency-key KEY --message-id ID --effects-reviewed`, только если владелец или доверенный оператор независимо установил, что это исходящее принадлежит именно исходной попытке. Одного совпадения текста недостаточно. Мост сверяет личный диалог, адресата, направление, текст, отсутствие reply-to и появление сообщения после последнего сообщения на момент подготовки. Без успешной ручной сверки и без квитанции Telegram исход остаётся `unknown`. Эта команда только сверяет исходящее.
- `rejected` означает подтверждённый отказ Telegram. Сообщи владельцу причину по `rejection_code`.

При прямой отправке действуют пауза, передача диалога человеку, непрочитанные указания и удержание из-за неизвестного исхода. Возобнови диалог через `job-client-control` только по явному поручению владельца. Новые входящие идут в обычный клиентский процесс [B2](B2.md). Правила возобновления описаны в [B4](B4.md).

### Ответ по клиентскому заданию

Ответ на входящее свяжи с точным reply-to, job/lease, актуальной revision и kind (`ack`, `result` или `clarification`). Сверь параметры через `--help`. Для отправки и `job-handoff` передавай `--history-pages N` из подтверждённого чтения. Мост сверяет число страниц и рассчитывает время проверки длинной истории.

Для исхода `answered` выполни `job-complete-reply --job-id ID --lease LEASE --receipt-key KEY`, если единственная предпринятая отправка помимо ACK — подтверждённый текст `kind=result`. Команда выполняет независимый readback, сверяет актуальную ревизию и фиксирует `answered`. При `job.state=completed` заверши ход. При потере результата команды проверь состояние через `job-read`. В остальных случаях отдельно сверь отправки и используй штатный `job-result`.

Для разных job-bound отправок одного `kind` в одной ревизии контекста указывай разные `--effect-slot`: целое от 0 до 31, по умолчанию 0. Например, текст и отдельное фото с `kind=result` могут использовать слоты 0 и 1. Для dry-run и apply одного эффекта сохраняй тот же слот и исходный ключ; неизвестный исход сначала сверяй, не меняя слот или ключ и не начиная новую отправку. Слоты разных `kind` независимы.

Для передачи клиентского задания используй `job-handoff` с теми же job/lease, актуальной `--expected-revision` и `--reply-to-message-id` исходного клиентского события: dry-run → apply с возвращёнными token/key → независимый `job-effect-readback --effect-key` исходного эффекта. Он отправляет одно уведомление владельцу и создаёт привязанную квитанцию `handoff`; дополнительный `notify-owner` не нужен. Сообщение о передаче самому клиенту, если требуется, отправляй через `send` с `kind=result`, без внутренней CRM-ссылки. После проверки эффектов перечитай задание и заверши `job-result --outcome handoff` с актуальной revision, всеми event_ids и проверенными квитанциями этого задания. Передай квитанцию `handoff` и квитанцию `result`, если отправил ответ клиенту. Обычный `send --kind handoff` для этого не используется; квитанция самостоятельного `notify-owner` не заменяет job-bound handoff.

Для `notify-owner` разреши актуальный `owner-target`, используй dry-run/apply, свежий token и один notification key на конкретное сообщение; проверь доставку. Эта привязка не меняет клиентскую роль входящих рабочего аккаунта по [B2](B2.md). При ошибке привязки или неизвестном исходе не заменяй адресат, ключ или способ отправки. Поводы клиентских уведомлений определяет клиентский скилл; самостоятельные вопросы директора — [M1](M1.md).

## СОСТОЯНИЕ

`probe`, `status`, `owner-status` показывают соединение и настройки. `monitor-status`, `monitor-events` показывают техническое состояние событий без чтения переписки.

CLI, аккаунты и служебные команды: [операционная инструкция Telegram](../references/telegram-runtime.md). Работа с диалогами и медиа: [Telegram skill](../../../.agents/skills/manage-owner-telegram/SKILL.md).

# D3 — SQLite + файлы

D3 — локальный слой хранения Manager. Название на карте объединяет несколько разных хранилищ: документы и навыки лежат в файлах проекта; отдельный файл хранит обезличенные агрегаты опыта по работам; SQLite Manager хранит служебное состояние выполнения процессов и контрольные точки интеграции. Поиск документации выполняет [D4](D4.md), состав файлов описан в [D5](D5.md).

## Что подтверждено кодом

- `docs/agent/` и `.agents/skills/` содержат руководства и навыки, которые Codex читает как файлы через A3.
- `private_knowledge/service_labor_experience.json` рядом с текущей SQLite Manager читается функцией оценки стоимости работ при наличии корректного файла; по умолчанию это `data/private_knowledge/`. Путь следует за постоянным каталогом данных, независимо от смены релиза. Это агрегированный опыт, не общая база поиска.
- `autostop_manager/storage.py` создаёт таблицы запусков Manager, внешних шагов и контрольных точек Store. Отдельная SQLite база автоматизаций хранит состояние заданий. Эти таблицы не являются индексом технических статей.
- Пространство [M2](M2.md) — `/var/lib/autostop-manager/roles/M2/`: состояние, индекс, недельные журналы и сводки вне Git и сменяемых релизов; оно включено в CRM backup.
- Таблицы `role_*` в существующей `/var/lib/autostop-manager-scheduler/registry.sqlite3` хранят дежурства M1/M2, привязки чатов, очередь, вопросы, решения и опыт. Изменения проходят через единственный automation controller. `/var/lib/autostop-manager/roles/M1/current-state.md` и `notes.md`, а также M2 `duty-state.md` и `notes.md` — читаемые представления этой базы. Их не редактируют как второй источник состояния; прежние журнал и `current-state.md` инженера сохраняются.

При поиске знаний выбирай нужный файл или специализированный инструмент; не предполагай, что любой документ можно запросить через SQLite или D1. Клиентские записи и переписка принадлежат своим рабочим системам.

Readback `get_manager_run` читает run, выбранные events и external steps в одной
SQLite read transaction; `list_manager_runs(include_events=true)` также сохраняет
единый snapshot. Lazy migration выполняет check-and-ALTER под общим SQLite writer
lock после initial schema script; отказ добавления столбца откатывает этот этап целиком.
Schema и значения уже существующих строк сохраняются.

Generic workflow transition проверяет вложенный `verification` тем же запретом
raw body keys, что checkpoint, до записи или принятия replay. Отрицательные executor,
verification и readback markers внутри массивов тоже запрещают `completed`;
diagnostic failure paths сохраняют индексы. Положительные вложенные technical refs
и существующие include flags остаются допустимыми.
Скалярные `false` и строки отрицательного результата (например, `failed`) в таких
массивах проверяются так же, включая вложенные списки и повторный `completed`.
Явный boolean success у readback/executor/verification node прекращает наследование
технического контекста к его generic payload children: доменный `status=failed`
в таком payload не означает неудачное чтение. Прямые противоречивые markers этого
node и явно названные вложенные check/checks/executor/verification/readback nodes
по-прежнему проверяются и запрещают `completed` при отрицательном результате.

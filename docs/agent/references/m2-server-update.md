# M2 — сервер, GitHub и обновление приложений

Это единый порядок M2 для подготовки, публикации, обновления и восстановления. Выпуск и перезапуск выполняются по текущему явному поручению. Сохраняй исходники, рабочие изменения и историю; проверяй опубликованную и установленную ревизии отдельно. До действий выбери физический installed snapshot по `REVISION` для live-контракта и checkout/worktree по HEAD/diff для подготовки выпуска; не подменяй один корень другим. Границы хостов: [host-operations.md](host-operations.md).

Одно разрешение покрывает описанный пакет, в том числе полученное через M1;
повторно его не спрашивай. Новый состав выпуска требует актуализации решения.
Публикация в ветку с автоматической установкой считается выпуском; перезагрузка
всего хоста поручается отдельно.

Прежний адрес [deployment.md](deployment.md) сохранён только для совместимости ссылок.

Обычный порядок: подготовь точные версии и проверенный способ возврата до окна;
в согласованное окно заверши работу, сделай одну согласованную копию и проверь
восстановление; установи эти версии, проверь службы и пользовательские сценарии;
при сбое останови этап и восстанавливай работу по сохранённому плану. Настоящего
универсального установщика эта инструкция не заявляет. Специальные процедуры ниже
нужны только для соответствующего изменения или явно порученной проверки.
По возможности подготавливай сборку, проверки и план переключения до остановки;
перенос копирования или восстановления за окно допустим только после проверки,
что полученная точка согласована и подходит для возврата выбранных версий.

## Публикация исходников

Если согласованный результат — ветка и PR для последующего ревью, подготовь изменения в отдельном worktree, выполни проверки затронутого поведения и дождись быстрого PR CI. Опубликуй коммиты обычным push, независимо сверь remote SHA и данные GitHub; в PR перечисли проверки и оставшуюся предрелизную приёмку. Merge, установку и полный ручной `release-rehearsal` оставь этапу квалификации выбранного после ревью релизного SHA. Публикация такого PR не требует остановки приложений, обновления installed skill или смены production pins.

Сохраняй другие checkout и чужие изменения. Не выполняй force-push основной
ветки; после согласованного merge или fast-forward независимо сверь точный SHA
удалённой основной ветки. Для Manager и CRM push и успешный CI сами по себе не
устанавливают релиз; Store workflow проверяй отдельно в разрешённых границах.

Рабочий порядок — обслуживание с полной остановкой приложений, описанное ниже.
Сохранившиеся cold/coordinated-компоненты не являются обязательным путём выпуска;
их удаление требует отдельной проверки связей. Открытые замечания старых review —
в [очереди обслуживания](../../maintenance-backlog.md).

Исправления проверяй короткими тестами затронутого поведения в отдельном worktree.
Собери один кандидат; канонический `release-rehearsal` выполняет
`./scripts/release-gates.sh` с одноразовыми данными для точного итогового SHA;
минимальная coverage — 82%. PR `quality` проверяет документы, lint и типы,
push не дублирует этот набор. Полный локальный прогон не повторяет уже успешный
канонический результат того же SHA. Повторный полный прогон нужен при изменении
проверенного кандидата или конкретном провале, а не для каждой промежуточной правки.
Подтверди точный remote SHA через `git ls-remote`. CRM сохраняет свой Python
registrar и guarded ledger; они не входят в native Manager MCP.

CI и source release gates используют `scripts/update-instruction-catalogs.py --check --project-only`:
проектная часть A4/A5 проверяется без локального кеша плагинов Codex. Source doctor также
использует `--project-only`. На целевом хосте отдельно запусти полный `doctor` и
`update-instruction-catalogs.py --check`, сверяющие установленные выбранные навыки
и host environment до выпуска. Эти проверки читают;
обновление каталогов без флагов выполняется до публикации исходников.

При выпуске изменений инструкций дополнительно сверь physical root/revision, весь граф с `MANIFEST.sha256`, профиль служебного исполнителя и источники, обнаруживаемые действующим Codex. Объём модельной проверки доставки AGENTS/профильных правил задаётся поручением владельца; для конкретного пакета он может её отменить. Проверки исходников, hashes и `skills/list` не доказывают загрузку правил моделью, в том числе при отменённой модельной проверке. Ошибка или неизвестный результат передачи правил не разрешает запуск клиентского хода или повтор исходного действия.

Если поручение ограничено готовым PR и зелёным CI, остановись на этой границе: merge,
установка/включение J1 VIN и серверный выпуск требуют отдельного объёма поручения.
Исходники новой функции, units/installers и обновлённые инструкции не доказывают работающий runtime.

Если готового результата точного кандидата нет, для отдельного Ubuntu runner
можно использовать GitHub workflow `release-rehearsal` с полным
`candidate_sha`. Он создаёт собственную `.venv`, выполняет неизменённый
`scripts/release-gates.sh` и только после успеха сохраняет Git archive и sealed
automotive export этой ревизии. Artifact содержит SHA-256 файлов, dependency receipt,
полный gate log и разные поля `source_revision`/`workflow_revision`: ревизия workflow
не подменяет проверяемый commit. Точный SHA задаётся через `workflow_dispatch`;
обычный push и PR не запускают второй полный прогон.
Workflow имеет только `contents: read`, не использует production secrets и не
выполняет серверный выпуск. Его green/artifact подтверждают исходники и synthetic
проверки; перед обновлением отдельно нужны текущие host, backup и runtime gates.

Для CRM используй точный итоговый SHA основной ветки и один успешный final
`quality.yml` с `export_tested_image`; устанавливай проверенный OCI image, не
пересобирая его на сервере. Детали сборки CRM и условную Windows-проверку смотри
в её `docs/OPERATIONS_RUNBOOK.md`. Store gates применяй только к разрешённым
изменениям Store и выбранному workflow, не запускай providers или write smoke на
реальных данных ради общего выпуска.

## Отдельная активация VIN-исследования J1

Самостоятельный [VIN-режим](j1-vin-research.md) по умолчанию выключен,
но два новых инструмента включены в source manifest и регистрируются при любом значении флага.
При разрешённом будущем выпуске сохранить прежний SHA и конфигурацию; общий приватный
`/etc/autostop-j1-vin.env` должен задавать одинаковый флаг Manager MCP и J1 worker.
До включения проверить root-owned `0700` tmpfs `/run/autostop-j1-vin`, 128 MiB budget,
согласованные RuntimeDirectory/Preserve/ReadWritePaths и локальный VIN runtime status.
Worker restart не должен удалять действующую job; после host reboot ожидается
`vin_ephemeral_state_lost`, без восстановления полного VIN из постоянного stub.

После штатной активации сверить installed SHA, все страницы `tools/list`, schemas/annotations,
состояния сбора/анализа и полный отдельно порученный цикл до финализации/expiry.
VIN-bearing browser URLs остаются запрещены; прежняя browser-аттестация нужна лишь для
обезличенных страниц. При отказе выключить способность и остановить дальнейшую сеть VIN-jobs
в рамках разрешённого rollback; возвращать код без проверки runtime недостаточно.
Эта инструкция сама не поручает активацию, merge или изменение CRM/Store/VPN.

## Обслуживание с остановкой приложений

1. Проверь полномочия для всех затрагиваемых компонентов; без разрешения не
   инспектируй Store и не начинай совместный выпуск. Зафиксируй опубликованные SHA,
   проверенные пакеты/images и фактические версии Manager, CRM и разрешённого Store.
   Сохрани незакоммиченную работу. Существующие checkout
   не переключай ради установки. Проверь совместимость итоговой пары Manager/CRM
   с выбранным Store и реальные пути source, Python, данных и конфигурации.
   Заранее определи и сверь порядок возврата прежних образов, конфигурации и bindings
   без перезаписи актуальных данных; новый или изменённый способ и конкретный сбой
   проверь в изолированной среде, не повторяя успешную проверку без причины. Для точной пары CRM/Manager
   проверь структуру и разрешения каталогов монтирования, включая вложенное
   подключение данных под read-only исходниками, на отдельном disposable mount
   с тестовыми данными без сети и без production mounts.
   До окна сравни revision работающего CRM image с полем
   `AUTOSTOP_AUTOMATION_CRM_REVISION` в shared backup identity и эффективных
   окружениях Manager и scheduler; учитывай порядок override и не выводи секреты.
   При несовпадении не используй старый MCP для копирования. В разрешённом окне
   останови writers и отдельно запусти проверенный CRM snapshot helper с revision
   фактически остановленного image; до и после копирования независимо подтверди
   тот же container ID, отсутствие перезапуска и всех writers. До запуска новой
   версии обнови shared identity и после запуска сверь effective значения процессов.
   При изменении способа копирования SQLite проверь обработку WAL/SHM на
   изолированных данных, не ослабляя проверку других изменений исходного дерева.
   `scripts/crm-snapshot.py` открывает SQLite только в закрытой временной копии;
   при ошибке копирования или изменении исходных файлов выпуск не начинай.
2. Посчитай пик места, памяти и времени именно выбранной установки, включая одну
   копию данных и временное проверочное восстановление. Сохрани минимум 2 ГБ
   свободного места сверх рассчитанного пика. Используй текущий расчёт, а не
   фиксированный порог из прежнего окна обслуживания.
3. В разрешённое окно закрой приём новых задач, сохрани состояния очередей,
   duty/hold и незавершённые операции. Выполни проверяемый
   [Store drain](manager-runtime.md#завершение-store-перед-остановкой-manager).
   Store drain не подтверждает завершение J1. Сверь отдельные активные работы
   и фактические параметры остановки служб. Сохрани PID и ControlGroup; дождись
   штатного завершения процесса и `populated=0` в `cgroup.events` сохранённой
   группы или её исчезновения. Только после этого запускай новую версию.
   Временный override допустим лишь при подтверждённой необходимости для точной
   исходной версии; сохраняй исходные настройки и удаляй его до старта кандидата.
   Если задача зависла или результат внешней операции неизвестен, новый writer
   не запускай.
   Останови приложения Manager, CRM и Store, подтвердив идентичность и завершение
   их процессов. SSH и текущая управляющая сессия должны продолжать работать.
   Зафиксируй исходное состояние watchdog и его таймера; останови таймер и уже
   выполняющееся восстановление, независимо подтвердив их завершение. Возвращай
   только ранее активный watchdog после приёмки; не меняй посторонние таймеры.
   Store drain, остановка, копирование и проверка восстановления Store допустимы
   только в прямо разрешённом владельцем объёме; без него общий выпуск не начинай.
4. При подтверждённой остановке writers сделай **одну согласованную копию**
   необходимых данных и настроек всех затрагиваемых приложений. Включи ссылки
   на копию Manager/CRM и одну копию Store его штатным helper; общая
   процедура не копирует Store второй раз. Сохрани
   credentials, principal IDs, сессии, очереди и историю идемпотентности.
   Для разрешённой разовой копии Store используй helper с новым пустым закрытым
   root в согласованном объёме: helper удаляет предыдущую owned-generation в
   переданном root. Не меняй штатный root и расписание и не создавай ещё одну
   копию без необходимых полномочий.
   Один раз проверь восстановление локально в изолированном каталоге/БД без
   доступа к клиентским каналам, затем удали проверочную копию. Независимый ПК
   для этого порядка не требуется. Штатные резервные копии сохраняются.
5. Установи точные проверенные версии, сохранив persistent bindings и доступы.
   Не меняй рабочие credentials при обычном обновлении; их ремонт или ротация
   требуют отдельного поручения. Проверь фактические настройки остановки службы:
   замена исходников сама по себе не обновляет установленный systemd unit. Тайм-аут
   должен соответствовать проверенному безопасному завершению задач J1.
   До запуска запиши revision выбранного CRM image в shared backup identity и
   эффективные окружения Manager и scheduler; сверь порядок EnvironmentFile,
   чтобы более поздний файл не подменял значение.
   Старый CRM `deploy.sh` и сложные release/J1/guard-контроллеры сохраняются для
   анализа; в обычном обслуживании их не запускай до отдельной согласованной
   переработки. Простой installer допустим лишь с заранее проверенными эффектами:
   без второй копии, активации старой инфраструктуры или самостоятельного открытия
   приёма задач. [Офлайн-каталоги](offline-catalogs.md) проверяются отдельно;
   существующий исправный кеш повторно не загружается.
6. Запусти выбранные приложения в согласованной последовательности. Независимо
   проверь installed SHA, process cwd/interpreter, image digest, конфигурацию,
   Manager → CRM → Store, API/MCP/UI и авторизацию. Проверь scheduler, очереди,
   wake/duty и доступность включённых функций без тестовых клиентских сообщений,
   заказов и платежей. Неизвестные старые операции автоматически не повторяй.
   Для установленного Manager подтверди MCP handshake, все страницы `tools/list`,
   manifest, схемы и annotations; дополнительные provider и browser probes зависят
   от изменения и полномочий.
   Повтори сравнение CRM backup identity с реально запущенными процессами; при
   несовпадении исправь effective identity, перезапусти затронутые процессы в
   разрешённом окне и проверь фактические новые PID снова до открытия приёма задач.
7. После общей приёмки открой приём задач и зафиксируй результат. Удали временные
   распаковки, проверочные каталоги и ненужные сборки; сохрани уникальную работу,
   текущие runtime, одну рабочую точку восстановления, журнал и штатные backups.

При неизвестном результате, незавершённом drain, нарушении владения или нехватке
ресурсов останови затронутый этап и сохрани данные. Автоматический запуск старого
writer и наложение старой БД поверх новых операций запрещены. Возврат версии
выполняется в пределах заранее согласованного пакета восстановления с сохранением
текущих данных; изменение этого пакета согласуй отдельно.

Store не переустанавливается, если его выбранная версия уже работает и совместима.
Пока актуальный workflow не проверен в разрешённых границах, считай push/merge
Store `main` потенциальной установкой и не выполняй без разрешения на выпуск. Явный
`Prepare release` проверяет точный `candidate_sha` и подготавливает image;
`Deploy VPS` получает этот SHA и успешный `preparation_run_id`, проверяет
происхождение artifact и устанавливает проверенный image без повторной сборки.
При существующей установке `Deploy VPS` также создаёт свою точку source/DB/uploads
и не принимает копию общего helper как вход. Поэтому его запуск после общей копии
создаст дополнительную копию: до выпуска выбери и проверь способ соблюсти состав
согласованной точки, не отключая защиту workflow и не делая лишнюю копию Store.
Изменения контракта проверяй на итоговой связке до открытия приёма задач;
поддерживать промежуточное сочетание старых и новых процессов при полной остановке
не требуется. Контракт — [store-api.md](store-api.md).

## Комплект для выпуска документации

Подготовка инструкций не устанавливает релиз, не перезапускает службы и не меняет
duty или живую структуру. При выпуске используй общий порядок выше; сверь CRM pin и
`content_hash` по [контракту каталога](automotive-tools.md). Путь Python выбирай по
фактическому `ExecStart`; отдельные clone и venv на сервере не обязательны. GitHub
push и количество tools не подтверждают загрузку инструкций или скиллов.

Если отдельно поручено обновление инструкций в конструкторе, получи свежий полный
технический owner graph по текущей schema
   `api:/api/manager_structure`; сохрани исходные JSON-типы чисел. Из exact sealed
   Manager и final bundle подготовь instruction-only patch вне репозитория:

   ```bash
   /opt/autostopcrm/.venv/bin/python /opt/autostopcrm/scripts/sync_manager_structure_instructions.py \
     --graph /ROOT_PRIVATE/fresh-graph.json --manager-root /ROOT_PRIVATE/sealed-manager \
     --bundle /ROOT_PRIVATE/final-catalog.json --patch-output /ROOT_PRIVATE/instructions.json
   ```

   Скрипт только готовит файл; preview/apply API не вызывает. Проверь
   `prepared_from_version`, `unchanged_scope_digest`, IDs и тексты. В порученном
   обновлении после fresh full read выполни `preview_requests` через owner API,
   затем exact `apply_requests` с предусмотренными CAS version и UUID/idempotency;
   после каждой записи независимо перечитай graph. При 409 или неизвестном исходе
   сначала readback/receipt и новая подготовка, без слепой смены ключа. Сохрани canvas,
   parent/геометрию, manual paths, связи и `tool_statuses`; E1 layout migration для текста
   не запускай. В браузере проверь pinned SHA ссылки, относительные переходы, unsafe URL
   блокировку и owner/viewer права; просмотр не запускает providers или business actions.

## Native MCP и подключённый Codex

Эти расширенные проверки выполняй для соответствующих изменений или по отдельному
поручению; общая приёмка не требует повторных вызовов всех providers.

Проверь active `autostop-manager-mcp.service`; cwd его `MainPID` должен совпадать с физическим target `/opt/autostop-manager-releases/current`. Probe запускай из `/tmp` с активным `PYTHONPATH`, чтобы checkout не подменил импорт. Перед примером задай `runtime_python` точным проверенным Python из текущего `ExecStart`:

```bash
manager_snapshot=$(readlink -f /opt/autostop-manager-releases/current)
env PYTHONSAFEPATH=1 PYTHONPATH="$manager_snapshot" "${runtime_python:?Set verified service Python}" -m autostop_manager.cli mcp-probe --url http://127.0.0.1:41931/mcp --provider-failure-check
```

Требуются handshake, все страницы `tools/list`, manifest/schema и annotation parity, безопасные вызовы. Только при отдельном разрешении на такую проверку Store добавь `--store-check`: он читает health/capabilities и не более одного заказа через `store_search(entity="store_order", limit=1)` без pagination и записи. Проверяй `checks.store_order_search.ok=true`; `store_order_sample_empty` означает доступ без образца для проверки полей. Отчёт не сохраняет ID, поля или raw provider errors. Без разрешения Store эту проверку не выполняй и укажи ограничение приёмки.

После `browser_ready=true` и `browser_containers_ready=true` повтори probe с `--timeout 90 --browser-check`; нужен `checks.fetch_page_browser.ok=true` для публичного `https://example.com/`. Container health не подтверждает всю Manager browser chain.

В существующем клиенте после активации отправь App Server `config/mcpServer/reload` (`params: null`), затем в новом ходе проверь `mcpServerStatus/list` и endpoint `tools/list`. Старый ход может сохранять прежние declarations. `partsapi_catalog_lookup` должен содержать `provider_parameters`, `supplier_id`; `norms_models` проверяется с lowercase make code сначала dry-run, затем разрешённым bounded catalog lookup. Подтверждение reload не заменяет вызов. Протокол: [OpenAI App Server](https://developers.openai.com/codex/app-server).

Для marketplace проверь `catalog_provider_status(stage="market_listing")` и четыре инструмента Avito/Drom. Avito: dry-run → bounded search → точное listing read. Drom запускается только после API access и `AUTOSTOP_DROM_LISTINGS_ENABLED=1`; queued task не равна результату. Подробности: [market-listings.md](market-listings.md). Auth/quota/provider ошибки отличай от transport. После проверок восстанови прежний work-mode.

## Новый вход в роль M2

Если пользователь явно поручил создать отдельный чат для проверки входа M2 после стабильной приёмки выпуска и обновления технического состояния, создай новый ephemeral Codex thread с обычным cwd `/opt/AutostopManager` и поручением работать инженером M2. Сохрани штатные базовые инструкции. Передай явный физический installed root с `REVISION` и отдельный source root с HEAD/diff, без изменения cwd или копирования runtime. Ограничь проверку чтением installed `AGENTS.md`, A1, M1, M2 и постоянных состояния M2, индекса и последней сводки по индексу. Переписка, клиентские кейсы, секреты, изменяющие инструменты, journal start/append и запуск исполнителей в этот smoke не входят.

Приёмка требует фактических завершённых чтений и совпадения SHA-256 всех семи файлов с независимым срезом до и после хода, а также живого `tools/list` с текущим schema fingerprint и annotations. Ответ агента без этих receipts не подтверждает загрузку. Сохраняй только технические hashes, статусы и ограничения; polling делай порциями до 60 секунд, после хода отпишись от ephemeral thread.

Ошибка первого чтения остаётся в отчёте; она восстановлена только после успешного чтения нужного файла с совпавшим hash. Журналы и история читаются через актуальный индекс M2, без копирования прежних рабочих кейсов. Внешние ограничения доступа оценивай отдельно от успешного входа в роль.

## Службы и восстановление

Установщики, включая `scripts/install-codex-wake.sh`, остаются техническими
инструментами со своими эффектами; перед использованием читай текущие flags и
реализацию. Их запуск не заменяет общий порядок обслуживания.

Сохраняй отдельные personal/work Telegram sessions, выбранный worker и закреплённые
инструкции, durable registry, незавершённые задания и их ID. Старый RAM-only комплект
не запускается поверх durable registry. Импорт исторических ссылок и выбор нового
worker не являются обязательным шагом обычного обновления; специальные случаи —
в [telegram-runtime.md](telegram-runtime.md).

Уже существующий hold или duty имеет владельца: обслуживание не даёт права снимать
чужое удержание. До возобновления проверь scheduler/socket/readiness, managed timers,
CRM/Telegram и исходные состояния управления. Неизвестный внешний эффект сначала
сверяется по точному результату; старый registry поверх новых операций не восстанавливается.

## Обновление ОС

Перед обновлением ОС сохрани root-only пакетный перечень, config служб/сети/proxy,
свежий проверенный dump и `/proc/sys/kernel/random/boot_id`. Используй поддерживаемые
обновления без снятия vendor phasing и автоматического удаления данных. Reboot —
отдельное поручение, после окончания deploy/backup процессов. После него проверь
новый boot ID, `uname -r`, SHA, systemd, containers, публичный TLS/HTTP, Gateway/MCP,
G1, Telegram duty, J1 static/browser и Codex.

При изменениях соответствующих компонентов используй их действующие gates:
Manager — `scripts/release-gates.sh` с одноразовой БД; CRM — `run_checks.ps1 -Profile ci`
и текущий CRM runbook; Store — `scripts/run-backend-tests.sh --agent-write-smoke`,
затем `--full`, если этот scope и workflow разрешены.
При failed backup/rollback, обязательном CI или неверном target SHA
выпуск останавливается.

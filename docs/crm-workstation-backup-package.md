# Пакет копирования CRM

Перед обслуживанием сверь установленный `REVISION` пакета, ревизию работающей CRM и раздельные результаты копирования, возврата служб и доставки. Процедуру выпуска определяет [инструкция M2](agent/references/m2-server-update.md); подтверждённые точки восстановления описаны в [регламенте копирования](agent/references/complete-backup.md).

Для согласованного выпуска пять проверенных файлов `crm_backup_coordinator.py`, `crm-snapshot.py`, `check-crm-snapshot-restore.py`, `deliver-crm-backup.py`, `transfer-crm-backup-windows.py` положить вместе в `/usr/local/libexec/autostop-crm-backup/`: root:root, каталог 0700, файлы 0600. Нужны `/usr/bin/python3` с `cryptography`, Docker, systemd и OpenSSH. SSH-алиас и закреплённый host key остаются в действующей root-конфигурации; секреты в пакет не копируются.

Собери пять файлов из одного согласованного полного Git SHA в новом закрытом каталоге. Запиши этот SHA в `REVISION`.
В `source-manifest.json` запиши JSON-объект, где ключи — имена пяти файлов, а значения — их SHA-256.
Из проверенного checkout Manager выполни сверку до установки, указав каталог подготовки.

```sh
python3 scripts/verify-crm-backup-package.py --revision "$candidate_sha" --package-dir "$staged_dir"
```

После установки повтори команду с тем же SHA и `--package-dir /usr/local/libexec/autostop-crm-backup`.
Скрипт только читает `REVISION`, точный набор записей манифеста и пять файлов. Он сравнивает их SHA-256 с манифестом и байтами локального коммита Git.
При любом ненулевом коде приостанови выпуск пакета и заново подготовь комплект из согласованного SHA.

Обновляй пакет целиком. Checker импортирует соседний snapshotter, а доставка
запускает coordinator для обновления статуса. Смешанный комплект может
отклонить исправный архив.

Для согласованной замены или отката выбери интервал между штатными запусками.
Подтверди завершение текущей попытки и отсутствие активных backup, recovery,
delivery и transient workers `crm-backup-*.service`. На время обмена возьми
без ожидания `coordinator.lock`, `operation.lock` и `delivery.lock` в каталоге
CRM-копии и `/opt/autostopcrm/.autostop-deploy.lock`. Занятый lock или близкий
запуск таймера требуют другого интервала. Согласуй отсутствие ручного запуска.
Краткий `pending.lock` применяется при публикации готовой копии.

Подготовь проверенный соседний каталог на той же файловой системе. Обменяй
его с действующим каталогом атомарно через `renameat2(RENAME_EXCHANGE)`.
Перепроверь оба комплекта по их SHA до освобождения блокировок. Для отката
повтори обмен и readback с теми же условиями. Сохраняй предыдущий комплект
до следующего подтверждённого копирования и доставки. После замены сверь
состояние обоих таймеров и их следующий штатный запуск.

В действующей конфигурации CRM сохранить mounts/networks/auth и установить `AUTOSTOP_CRM_BACKUP_CONTROL=1`. Scheduler и backup service должны получать `AUTOSTOP_AUTOMATION_CRM_REVISION` точной принятой CRM-ревизии из общего `/etc/autostop-manager/crm-backup-identity.env` (root:root 0600). На MNG1 scheduler уже читает его через последний identity dropin, backup service — через `EnvironmentFile`. Пустое, неверное или несовпадающее значение запрещает остановку CRM. Учесть порядок EnvironmentFile и проверить только это поле работающего scheduler, не выводить окружение. Исторические конфигурации не переписывать.

Рабочее состояние находится в `/var/lib/autostop-manager/crm-backup/`, каталог root:root 0700, файлы 0600. Там хранятся журнал попытки, архив с ключом OAuth, указатель pending и технический журнал доставки. Запись статуса M2 — `/var/lib/autostop-manager/roles/M2/crm-backup-status.md`, root:root 0600. `pending.lock` защищает только выбор и публикацию поколения; передача не удерживает его во время сети.

Доставку разрешает устойчивый `pending-ready.json` для полностью записанного архива после подтверждённого возврата служб. Журнал попытки и журнал доставки обязательны; ошибка их записи не разрешает удалять прежние копии. Страница M2 — отображение этих журналов: её временная недоступность не отменяет готовую копию и не блокирует возврат служб или доставку. Следующая попытка доставки повторяет обновление страницы, даже когда pending уже отсутствует. Завершённые transient workers автоматически освобождаются systemd; их результат хранится в журнале попытки.
При `ssh_unknown` журнал службы содержит фиксированные метки `stage` и `reason`, а `ssh_exit_255` обозначает только код завершения процесса SSH.

После прерванной публикации нового архива служба доставки может вернуть в
очередь прежнюю готовую копию. Она сверяет точную завершённую попытку, оба
локальных файла и хеш прежней копии. При наличии следов доставки для одного
из этих поколений или расхождении доказательств сохраняется ошибка
`pending_not_ready`. Метка `crm_pending_repaired=previous_ready` означает
локальное восстановление указателя. Сами архивы и журнал попытки
сохраняются, а доставка выполняется на следующем штатном запуске.

Установить пять файлов `deploy/systemd/autostop-crm-{workstation-backup.service,workstation-backup.timer,workstation-recovery.service,backup-delivery.service,backup-delivery.timer}` и `autostop-manager-scheduler.service.d/crm-backup-start.conf` как root:root 0644. Проверить `systemd-analyze verify`, затем `daemon-reload`. Backup service вызывает recovery через `ExecStopPost`; отдельный worker завершает начатый stop. Recovery стартует после Docker и повторяется при ошибке. Scheduler dropin задаёт `TimeoutStopSec=infinity` для native drain и read-only `ExecCondition`, сохраняющий исходно выключенный scheduler до завершения попытки. До первой попытки, после её завершения и для исходно активного scheduler запуск разрешён. Проверить effective `TimeoutStopUSec=infinity`: на MNG1 прежний пакет использует отдельный host override, одних базовых 30 секунд недостаточно.

До первого включения подтвердить остановку всех writers, возврат служб после сбоя и изолированное восстановление с ключом. После приёмки включить recovery service и оба таймера; на принятом MNG1 сохранить расписание. Readback: hashes пакета/REVISION, точный CRM image/revision и control flag, effective scheduler identity/timeout, активность units, `list-timers` и `LastTriggerUSec`. Backup — 02:00 Asia/Krasnoyarsk, `Persistent=false`. Таймер доставки проверяет очередь через 2 минуты после загрузки (`OnBootSec=2min`) и примерно каждые 10 минут после предыдущей активации службы (`OnUnitActiveSec=10min`), независимо от работы агента в роли M2. Архив доступен для передачи после подтверждённого возврата служб и публикации `pending-ready.json`. В M2 сверить назначение и отдельные фактические результаты копии, возврата и доставки; checkpoint не выдавать за календарный запуск. ПК `DESKTOP-7RAOHT7`, alias `autostop-pc`, путь `C:\Users\9860606\Desktop\Резерв CRM`: подтвердить размер, SHA-256 и закрытый ACL итогового файла. Хранить две подтверждённые копии на ПК и одну последнюю непереданную на сервере; неудача не удаляет прежнюю. Ежедневные restore/tests не нужны.

После перезагрузки `LastTriggerUSec` таймера копирования может быть пустым.
Сверь текущее состояние и настройку автозапуска обоих таймеров по отдельности.
Запущенный вручную таймер может работать до перезагрузки при выключенном автозапуске.
Последний запуск сверь по журналу backup service, включая предыдущую загрузку,
и сохранённому журналу попытки. Результат доставки проверь по квитанции и
фактическим файлам на ПК. Пустая очередь доставки подтверждает только отсутствие
ожидающих передач.

При успешной доставке `delivery-status.json.at` хранит время подтверждения итогового
файла для текущей попытки. Повторная ротация или локальная очистка сохраняет это
время. Старые квитанции `delivered.json` содержат идентификатор и контрольную сумму,
поэтому по ним нельзя восстановить точное время подтверждения прошлой копии.

Одноразовые скрипты первого перехода удалены из текущего пакета; [исторический результат](https://github.com/UgaChavis/AutostopManager/blob/bb975f36cafa806cd9ebe98c455d7238a84e3f55/docs/crm-first-transition-20261031.md) сохранён. Для будущего выпуска использовать текущую процедуру обслуживания CRM.

## Проверка восстановления CRM

При создании архива проверяются JSON-объекты состояния, настроек и пользователей. Ошибка оставляет прежнюю опубликованную копию.
Перед проверкой восстановления сверь размер и SHA-256 с записью о выбранной копии. Оригинал используй только для чтения.
Запусти `check-crm-snapshot-restore.py --archive <архив> --destination <пустой_закрытый_каталог>` от проверенного комплекта.
Скрипт распаковывает данные и ключ OAuth, сверяет целостность дерева, JSON-объекты, SQLite и расшифровку.
Пакет сверяет версию журнала изменений CRM при создании и при восстановлении
копии. Для текущей CRM допустимы версии 1–4 и исходная БД без метки версии,
которую инициализирует сама CRM. При переходе CRM на новую схему проверь
совместимость пакета и запуск восстановленного приложения.
Зафиксируй результат проверки архива отдельно от результата запуска приложения.

1. Сверь локальный образ с `crm_image` и `crm_revision` из manifest. Используй тот же образ по digest, `--pull never` и штатную команду.
   Если образу нужен Manager, отдельно скопируй совместимую ревизию его кода и статических ресурсов, сверив файлы с manifest.
   Подключи эту копию только для чтения и выдели пустое временное хранилище Manager.
2. Используй одноразовый контейнер с `--network none`, без опубликованных портов и автоперезапуска. Запусти его от штатного пользователя
   образа с корневой файловой системой только для чтения. Подключай только закрытые проверочные копии. Храни OAuth-файл
   из архива, ключ и `runtime-config.json` вне контейнера. Настрой одноразовую авторизацию и loopback для API и MCP.
   Рабочие окружения, тома и сокеты оставь вне проверки. Отключи фоновые агенты, обработку очередей и внешние интеграции.
   Для проверочного контейнера задай `AUTOSTOP_CRM_BACKUP_CONTROL=0`.
3. Заранее рассчитай запас места и памяти для архива, распакованной копии и процесса CRM. Для `tmpfs` учитывай
   архив и распакованные файлы в расходе памяти. Задай контейнеру лимиты CPU и памяти без swap, наблюдай за запасом памяти хоста.
   Проверенную временную копию архива можно удалить перед запуском.
4. Запусти контейнер. Внутри проверь HTTP `200` на `/api/health` и `401` от MCP и доски при запросах без авторизации. Прочитай доску
   с одноразовым API-ключом и сверь на месте наборы идентификаторов активных карточек и колонок с распакованным состоянием.
   В отчёт перенеси только технический результат. Эта проверка запуска охватывает CRM с тестовой авторизацией и пустым
   состоянием Manager. Сохранённый OAuth проверяется при распаковке.
5. Подтверди штатное завершение и удаление контейнера и проверочного каталога. В одном прогоне архив занял 134 МиБ,
   рабочий каталог после удаления временного архива — 461 МиБ, пик памяти контейнера составил 357 МиБ,
   весь прогон занял 135 секунд. Эти замеры относятся к одной копии.

Если `docker image inspect` завершается с `pthread_create failed` из-за унаследованного `RLIMIT_AS`, ограничивай виртуальную
память проверяющего процесса только на время проверки архива. Временно изменяй мягкий предел, сохраняя жёсткий.
Восстанови исходный мягкий предел перед вызовом Docker, сохранив лимит памяти контейнера и контроль памяти хоста.

Перед заменой рабочих данных отдельно сохрани текущее состояние и останови writers по [процедуре M2](agent/references/m2-server-update.md#обслуживание-с-остановкой-приложений).
Старые очереди и неизвестные внешние действия автоматически не воспроизводи.
